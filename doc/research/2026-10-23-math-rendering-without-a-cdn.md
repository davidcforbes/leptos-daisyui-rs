# Compile math-core into the wasm, retire KaTeX

> **Implemented 2026-10-23 (ldui-r0co, fork/main `e14945d`)** as recommended:
> math-core compiled into the wasm, see `src/markdown/math/`. Two changes from
> the plan below, both found while building it: the depth guard became a
> stack simulation driven by math-core's own command arities (two security
> reviews found bypasses of a plain brace counter), and its cap is 20 entries
> in debug builds and 64 in release, because an unoptimised build spends
> about 16 times more stack per level. No math font is vendored; system MATH
> fonts are used. Research notes and measurement scripts are in
> [`2026-10-23-math-rendering-without-a-cdn/`](./2026-10-23-math-rendering-without-a-cdn/).

**Recommendation: replace the `window.katex` hook with the pure-Rust `math-core` crate, compiled into the library's wasm. It turns LaTeX into native MathML Core with no JavaScript, no worker and no asset the host has to serve.** That makes math work under 4iiz-Office's `script-src 'self'` with nothing to configure. The measured cost is about **+66 KB brotli** (+202 KB raw) of wasm, and it returns a typed `Result` with a byte range, which maps directly onto a "leave the source visible" fallback. Its known gaps against KaTeX are **52 of about 1,046 commands**, mostly rare. Its one real hazard is that **deeply nested input overflows the wasm stack and traps**, which in a CSR app kills the UI. A cheap lexical depth guard (cap 64) must therefore run before every conversion, and the converter's output must still pass a Rust MathML allow-list before it reaches the DOM. The runner-up is to vendor **Temml 0.14.0** (about 182 KiB, MIT, zero advisories) into a same-origin worker exactly like `assets/pele/`. That is the right fallback if the browser lane shows math-core's visual quality is unacceptable. KaTeX's own HTML mode keeps the best fidelity, but its markup carries **16 to 24 inline `style` attributes per formula**, SVG, and class names that changed in 0.18.0. That makes it the most brittle choice to sanitise and the most exposed to a strict `style-src`. Everything below rests on registry data, primary docs and local wasm builds made on 2026-10-23. Visual quality has not been checked in a real browser, so the first browser-lane run is the deciding test.

## Office's CSP blocks math today, and seven routes could fix it

`src/markdown/math.rs` looks for a `window.katex` global and, when it finds one, calls `katex.render(formula, el, {displayMode, throwOnError:false})` on each `.math-inline` and `.math-display` element. The module's own doc comment tells consumers to load KaTeX from `cdn.jsdelivr.net`. Under 4iiz-Office's `script-src 'self'` that script never loads, so the global is absent and every formula stays as raw `$…$` source. The fix has to satisfy the constraints `pele` already met for Mermaid: no CDN, no `eval`, output that a Rust allow-list can sanitise, and clean axe results in both light and dark themes.

There are two families of answer. The first keeps a JavaScript renderer but serves it same-origin, ideally in a worker: KaTeX, Temml or MathJax 4. The second drops JavaScript entirely and compiles a Rust converter into the wasm: math-core, pulldown-latex, katex-rs or RaTeX. One trap sits between the two. The old `katex` crate (xu-cheng, 0.4.6), which `mdbook-katex` depends on, is not a Rust renderer at all. On wasm32 its `wasm-js` backend runs the bundled `katex.min.js` through **`js_sys::eval`**, which `script-src 'self'` without `'unsafe-eval'` blocks ([wasm_js.rs](https://github.com/xu-cheng/katex-rs/blob/master/src/js_engine/wasm_js.rs)). That rules it out on the very CSP that motivates this work.

## Self-hosting a JavaScript renderer works, but builds a second pele

All three JavaScript renderers can be served same-origin under `script-src 'self'`. **KaTeX 0.19.0** (released 2026-10-01, MIT) contains zero `eval`, `new Function` or `innerHTML` calls. Its `renderToString` ran in a DOM-free context in both output modes, so it fits the existing worker pattern unchanged ([katex.min.js 0.19.0](https://cdn.jsdelivr.net/npm/katex@0.19.0/dist/katex.min.js)). A full HTML-mode self-host is `katex.min.js` (272,868 B), `katex.min.css` (24,793 B) and 20 woff2 fonts (259,792 B). The CSS points at the fonts with relative URLs, so it needs no rewriting ([jsDelivr listing](https://data.jsdelivr.com/v1/packages/npm/katex@0.19.0?structure=flat)). The problems are in the markup and the release history. HTML mode emitted **16 inline `style` attributes for `x^2+\frac{a}{b}` and 24 for a sized radical with `\sum`**, plus SVG paths for radicals and tall delimiters. Release **0.18.0 prefixed KaTeX's CSS classes and warned that "allowlists targeting KaTeX's internal classes must update their selectors"** ([KaTeX CHANGELOG](https://raw.githubusercontent.com/KaTeX/KaTeX/main/CHANGELOG.md)). The prefixing in 0.19.0 is partial (`katex-base` sits beside a bare `mord`), so a class allow-list would have to be rebuilt on every upgrade, at a cadence of 34 releases in the first nine months of 2026 ([npm registry](https://registry.npmjs.org/katex)). KaTeX's `output:'mathml'` mode removes the CSS, the fonts and every inline style, but it was designed as an accessibility shadow for the HTML rendering. Its matrices rely on `mtable@columnalign`, `rowspacing` and `columnspacing`, **none of which Chrome supports** ([MDN BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)).

Every KaTeX XSS-class advisory has sat in the `trust` and URL paths: protocol normalisation (CVE-2024-28246), `\includegraphics` escaping (CVE-2024-28245), `\htmlData` attribute names (CVE-2025-23207), and a 2026 prototype-pollution bug that could flip `trust` on (GHSA-238p-pmpm-9mq7, fixed in 0.18.2). The advisory itself notes that exploitation "requires the consuming application to insert KaTeX output into a web page without a separate sanitizer" ([GHSA-238p-pmpm-9mq7](https://github.com/advisories/GHSA-238p-pmpm-9mq7)). KaTeX's own security page recommends sanitising with "a rather generous whitelist (including some of SVG and MathML)" ([KaTeX Security](https://katex.org/docs/security)). With `trust:false`, local tests on 0.19.0 turned `\href{javascript:…}`, `\htmlData` and `\includegraphics` into red error text. With `trust:true`, the output contained `href="javascript:alert(1)"`. So a JS renderer is safe here only when pinned at 0.18.2 or later, run with `trust:false`, and given a finite `maxSize` (the default is Infinity), with a Rust allow-list behind it.

**Temml 0.14.0** (2026-10-08, MIT, no dependencies) is the strongest JavaScript option for this library. It is derived from KaTeX but emits compact MathML: `temml.min.js` is 167,881 B, and `Temml.woff2` is 9,404 B, served next to one Temml CSS file of about 9 KB ([jsDelivr listing](https://data.jsdelivr.com/v1/packages/npm/temml@0.14.0?structure=flat)). It has **zero published security advisories** ([GitHub Advisory DB](https://api.github.com/advisories?ecosystem=npm&affects=temml)). The math-core author judges that Temml "produces much higher quality MathML output than KaTeX" because it ships per-browser CSS workarounds ([math-core README](https://github.com/tmke8/math-core)). Its costs are a single maintainer and the font story. Temml's lightweight system-font mode "has rendering issues. Chrome and WebKit both botch extensible arrows", and the recommended Latin Modern font (about 380 KB) is not in the npm package ([Temml Administration](https://temml.org/docs/en/administration)).

**MathJax 4.1.3** (Apache-2.0) is the only candidate with npm SLSA provenance ([npm registry](https://registry.npmjs.org/mathjax)), and it has the richest built-in accessibility. It is also four to seven times heavier: `tex-chtml.js` is 997,445 B, and the default font package adds 105 woff2 files totalling 1,623,040 B. Its default accessibility stack builds its speech worker from a **`blob:` URL** ([tex-chtml.js](https://cdn.jsdelivr.net/npm/mathjax@4.1.3/tex-chtml.js)), which `worker-src` falls back to `script-src 'self'` to block. MathJax is also designed to typeset the page DOM itself, which does not fit a "render a string, sanitise in Rust" pipeline.

Any of the three would need a second copy of pele's machinery: a vendored bundle, a SHA-256 pin (KaTeX and Temml publish no npm provenance), a same-origin worker URL that every consumer must serve and can relocate, an asynchronous render queue with a timeout, and a host-configured asset base. The editor's display-only math path, which is synchronous today, would become asynchronous. That is a reasonable price for Mermaid, which has no Rust alternative. For math, a Rust alternative exists.

## math-core gives MathML Core for 66 KB and a typed error

Local builds compiled every pure-Rust candidate for `wasm32-unknown-unknown` with no wasm-bindgen, using `opt-level="z"`, LTO and `panic="abort"`, and measured each against an 18 KB baseline module ([local measurement](./2026-10-23-math-rendering-without-a-cdn/measurements/)). The three MathML converters cost almost the same: **math-core +202 KB raw / +66 KB brotli, pulldown-latex +206 / +62, tex2math +204 / +67**. katex-rs costs +794 / +211 because it reproduces KaTeX's HTML span tree, which still needs KaTeX's CSS and fonts. RaTeX costs +2.26 MB / +495 KB before any fonts, because it lays glyphs out as SVG. The baseline already contained `alloc`, and wasm-opt was not run, so the true increment inside the Leptos binary should be somewhat smaller; that has not been measured.

On fidelity and correctness, math-core separates itself from the other two MathML converters. Its comparison table (taken from Temml's and run against KaTeX 0.17.0) marks **52 of about 1,046 commands** as unknown ([math-core comparison](https://tmke8.github.io/math-core/comparison.html)). The gaps are mostly `\dots*` variants, `\smash`, `\rlap`/`\llap`, `\colorbox`, `\substack` and mhchem `\ce`. Of these, only `\substack` and `\colorbox` are likely to appear in chat or notes content. A local 32-case corpus covered fractions, `aligned`, `align`, `pmatrix`, `cases`, `array` with `\hline`, accents, the `\mathbb`/`\mathcal`/`\mathfrak`/`\mathscr` alphabets, `\text`, `\color`, big operators, `\binom`, `\underbrace`, `\boxed` and `\cancel`. math-core rendered every mainstream case. It failed only `\ce` and a `\newcommand{\R}`, because it predefines `\R`. pulldown-latex 0.8.0 failed the font line, the `\boxed`/`\cancel` line and the macro line. More seriously, it **emitted unescaped `<` and `&` in text nodes** (`<mo><</mo>`), which is not well-formed markup. It also slowed quadratically on nested `\sqrt`, taking **10.7 s at depth 10,000**, and it has two open panic issues on malformed input ([#57](https://github.com/carloskiki/pulldown-latex/issues/57), [#58](https://github.com/carloskiki/pulldown-latex/issues/58)). tex2math is licensed **LGPL-3.0-only**, which raises a compliance question when it is statically linked into a single wasm. It has 237 downloads, and by default it silently renders unknown commands as identifiers ([tex2math](https://github.com/twn39/tex2math)).

math-core's API is a good fit for a fallback. `convert_with_local_state(latex, display)` returns `Result<ConvertResult, Box<LatexError>>`. The error carries a byte range and `error_message()`, with messages such as `Unknown command "\foo".` ([LatexError](https://docs.rs/math-core/latest/math_core/struct.LatexError.html)). Macro expansion is capped by `MaxExpansions`, whose **default of 1,000 matches KaTeX's `maxExpand`** ([MaxExpansions](https://docs.rs/math-core/latest/math_core/struct.MaxExpansions.html)). Locally, a self-recursive `\newcommand` and a 10⁶-expansion bomb were both rejected in 2 to 6 ms. `\href`, `\url`, `\htmlId` and `\includegraphics` are unknown commands, so they come back as errors, never as attributes, and `\text{<script>}` is escaped. With `default-features = false` the crate is `no_std` plus `alloc`, and none of its dependencies use threads or timers ([math-core Cargo.toml](https://github.com/tmke8/math-core/blob/main/crates/math-core/Cargo.toml)). Its stated goals include "definitely don't use JavaScript in any way" and "keep the compiled WebAssembly code small" ([math-core README](https://github.com/tmke8/math-core)).

The strongest outside signal is institutional. **Rust RFC 3958, "Rustdoc LaTeX math", merged on 2026-05-01**, and the open implementation PR adds `math-core` to `librustdoc` together with a MathML stylesheet and a modified Noto Sans Math font ([rust-lang/rust#156032](https://github.com/rust-lang/rust/pull/156032)). That PR's author is math-core's third-largest contributor. The PR has not merged, so this is an endorsement in progress. math-core's bus factor is still about one (tmke8 has 1,458 commits), and that is the main maintenance risk. It is mitigated by an MIT licence, a small pure-Rust codebase this repository could fork, and a `MathML in, allow-list out` boundary that would let Temml be swapped in behind the same sanitiser.

**The hazard is stack depth.** On wasm's default 1 MiB stack, math-core traps with `memory access out of bounds` at **451 nested `\frac`, 797 nested superscripts and 849 nested braces**. The repository contains no recursion limit, only a fuzz target ([math-core fuzz](https://github.com/tmke8/math-core/tree/main/fuzz)). katex-rs traps even earlier, at 203 nested `\frac`. tex2math (limit 64) and RaTeX return errors instead. A wasm trap is not a catchable panic: in a CSR app it leaves the instance unusable. Inside Leptos, the call stack already holds frames when math renders, so the real headroom is below the measured figures. The guard described below is therefore mandatory, not optional hardening.

## Native MathML is ready if the library ships a font and a fixes sheet

Choosing math-core means handing layout to the browser, and in October 2026 that is viable. All three engines render the MathML Core element set. On the WPT `/mathml/` suite, **Chrome 156 passes 97.7% of subtests, Firefox 158 83.1% and Safari 27.0 85.6%** ([wpt.fyi](https://wpt.fyi/results/mathml?label=master&label=stable)). MathML has never been an Interop focus area, including in 2026 ([Interop 2026](https://github.com/web-platform-tests/interop/blob/main/2026/README.md)), so convergence will stay slow. The known weak spots, documented by Temml's author, are extensible arrows and radical degrees in Chromium and WebKit, short `\left(` delimiters in WebKit, and inline line-breaking, which does not work in WebKit ([Temml: Browser Issues](https://temml.org/docs/en/administration)). Chrome deliberately skips the non-Core extras: **no `menclose`, no `mtable` spacing or alignment attributes, no `mlabeledtr`**. Safari ignores `scriptlevel` and gained `math-depth` only in 26.4 ([MDN BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)). This is why math-core requires its `mathmlfixes.css`, which resets `mtd` padding, polyfills `menclose` in Chromium for `\cancel`, and fixes accent margins. Its alignment environments use inline `text-align`, `justify-items` and `padding` styles instead of `mtable` attributes ([math-core README](https://github.com/tmke8/math-core)).

Fonts matter more than browser choice. MathML Core says "there is no guarantee that the fallback options provided will provide good enough rendering" without an OpenType font that has a `MATH` table ([MathML Core §5](https://w3c.github.io/mathml-core/#opentype-math-table)). The UA stylesheet sets `font-family: math`, which resolves to Cambria Math on Windows and STIX Two Math on macOS 13+ ([MDN: Fonts for MathML](https://developer.mozilla.org/en-US/docs/Web/MathML/Guides/Fonts)). Android and Linux are the least predictable. Self-hosted options measured as woff2 are **Fira Math 95,524 B, Latin Modern Math 388,212 B (GUST licence) and STIX Two Math 558,644 B** ([MathFonts](https://fred-wang.github.io/MathFonts/)). math-core recommends its own patched fonts, with a New Computer Modern subset of about 450 kB, or about 200 kB without `ssty` ([math-core README](https://github.com/tmke8/math-core)). KaTeX's fonts lack a MATH table and cannot be reused.

Theming works in the library's favour. The `math` UA rule resets the font, spacing and display **but not `color`** ([MathML Core Appendix A](https://w3c.github.io/mathml-core/#user-agent-stylesheet)), so formulas inherit daisyUI's `base-content` and switch with `data-theme`. Fraction bars and radicals are painted in the text colour. Two things break dark mode. `merror` has a hard-coded `lightYellow` background with a red border, and any `\color`, `mathcolor` or `mathbackground` value pins a colour that can vanish on a dark theme.

Accessibility is the biggest change from KaTeX's HTML rendering. **NVDA 2026.1 ships MathCAT built in**, which reads native MathML as speech and Nemeth/UEB braille with structural navigation and no add-on ([NVDA What's New](https://www.nvaccess.org/files/nvda/documentation/changes.html); [MathCAT](https://daisy.github.io/MathCAT/)). Putting an `aria-label` on `<math>` would replace that structure with a flat string, so the library must not add one. axe-core has **no rule that targets MathML** ([axe-core rules](https://raw.githubusercontent.com/dequelabs/axe-core/develop/doc/rule-descriptions.md)). The existing light/dark axe runs will catch contrast on math text, but not unspeakable or empty math, so the browser lane needs its own structural assertions. No 2026 source was found for VoiceOver, TalkBack or Narrator quality.

## Integration plan: one allow-list, a depth cap of 64, styles through the CSSOM

The pipeline replaces `render_one` in `src/markdown/math.rs`. It runs synchronously on the main thread, so `render_math` and `render_math_display_only` keep their signatures, and the editor's rule of rendering only display math stays intact. It mirrors `src/pele.rs`, with one deliberate improvement: **the sanitised tree is built into the DOM with `createElementNS`, never re-serialised into `inner_html`**. With no second parse, the namespace-confusion mutation-XSS class that has repeatedly bypassed DOMPurify cannot occur ([PortSwigger Research](https://portswigger.net/research/bypassing-dompurify-again-with-mutation-xss)).

| Step | What to build | Where |
|---|---|---|
| 1. Dependency | `math-core = { version = "0.9", default-features = false }` (no_std + alloc, no `ariadne`). Put it behind a default-on `math` cargo feature so non-Markdown consumers can opt out. Pin the exact version: the vocabulary below is version-specific. | `Cargo.toml` |
| 2. Depth guard | A pure lexical pre-scan that runs before conversion and rejects (a) more than **4,096 bytes** per formula, (b) **combined nesting above 64**, and (c) unbalanced groups. Nesting is `{`, `\left`, `\begin{…}`, plus one level for each control word directly followed by another control word (`\sqrt\sqrt…`, `\frac\frac…`), since unbraced chains recurse without braces. A cap of 64 is tex2math's default and sits about 7× below math-core's lowest measured trap (451). | new `src/markdown/math/guard.rs`, native-tested |
| 3. Convert | `LatexToMathML` built once (cached in a `thread_local`), with `MaxExpansions` left at 1,000 and `global_group` false. Do **not** set `ignore_unknown_commands`: it paints red text that fails dark-mode contrast. | `math.rs` |
| 4. Parse | Parse the output with `DOMParser` (`text/html`, an inert document) and walk only MathML-namespace elements into a `MathNode` tree, the counterpart of `svg_tree_from`. Non-MathML nodes are dropped and counted. | `math.rs` |
| 5. Sanitise | `sanitize_math_tree`, a pure function unit-tested with hand-built trees as `sanitize_svg_tree` is (allow-list below). | new `src/markdown/math/sanitize.rs` |
| 6. Build | `create_element_ns(MATHML_NS, …)`, then `set_attribute` for allow-listed attributes and **`style().set_property()` for allow-listed declarations**, then text nodes. Wrap the content as `math > semantics > [mrow(children), annotation encoding="application/x-tex"]` holding the original source, then replace the host element's children. | `math.rs` |
| 7. CSS | Vendor math-core's `mathmlfixes.css` at the pinned version into a stylesheet the consumer `@import`s next to `styles/tokens.css`, with a SHA-256 test like `PELE_BUNDLE_SHA256`. Add `merror { background: transparent; border-color: var(--color-error); color: inherit }` and a `math { font-family: "<chosen>", math }` rule. | `styles/math.css` |
| 8. Font | One woff2 in `assets/math-fonts/`, declared with `src: local(…), url(…) format("woff2"); font-display: swap`, so machines that already have the font skip the download and the file loads only when a `<math>` is present. | `assets/math-fonts/` |
| 9. Errors | On a guard rejection or `Err(LatexError)`, leave the `$…$` source exactly as today, then add `data-math-error="guard\|parse"` and put `error_message()` in `title`. The text stays `base-content`, so it passes contrast in both themes. | `math.rs` |
| 10. Lane | A new `cargo xtask test-math` lane: a fixture page served under `script-src 'self'`, axe through `common::axe` in light and dark, structural checks (every rendered host has a `<math>` with element children and a TeX annotation, no `aria-label`, `display="block"` on display math), and the hostile corpus (depth 500 to 20,000, macro bombs, `\href{javascript:}`, `\text{<script>}`), asserting **the page is still responsive afterwards**. Register it and confirm the test count changes. | `xtask/`, `tests/math/` |

**The allow-list** follows math-core's measured output vocabulary, intersected with MathML Core and the WHATWG Sanitizer's safe default ([WHATWG HTML: built-in safe default](https://html.spec.whatwg.org/#built-in-safe-default-configuration)), plus `semantics` and `annotation`, which the library adds itself.

| Kind | Allowed | Rule |
|---|---|---|
| Elements | `math, semantics, annotation, mrow, mi, mn, mo, mtext, ms, mspace, mfrac, msqrt, mroot, msub, msup, msubsup, munder, mover, munderover, mmultiscripts, mprescripts, mtable, mtr, mtd, mpadded, mphantom, mstyle, merror, menclose` | Anything else is dropped together with its subtree. `annotation` and token elements may hold text children only, never elements. |
| Global attributes | `display` (on `math`, values `block`/`inline`), `displaystyle` and `scriptlevel` (`true`/`false`/integer), `mathvariant` (fixed keyword list), `dir` (`ltr`/`rtl`) | Enumerated values only. |
| Per-element attributes | `mo`: `form, fence, separator, stretchy, symmetric, largeop, movablelimits, lspace, rspace, minsize, maxsize`. `mfrac`: `linethickness`. `mover`/`munder`/`munderover`: `accent, accentunder`. `mspace`/`mpadded`: `width, height, depth, lspace, voffset`. `mtd`: `columnspan, rowspan`. `menclose`: `notation` restricted to known tokens. `annotation`: `encoding` must equal `application/x-tex`. | Lengths must match a number plus a unit (`em`, `ex`, `pt`, `px`, `%`, `mu`), or a keyword. |
| `style` | Parsed into declarations and re-applied through the CSSOM. Only `text-align`, `justify-items`, `padding[-side]`, `border[-side]` (`solid`, `currentcolor`, an em length) and `width` survive. Values go through pele's existing `css_functions_are_safe`/`STYLE_FORBIDDEN` checks (no `url(`, `var(`, `expression`). | `color` is dropped in v1. |
| Always dropped | `href`/`xlink:href` on every element (Safari still follows `href` on any MathML element), `<a>`, `maction`, `annotation-xml` (an HTML integration point), `mglyph`, `malignmark`, `on*`, `id`, `data-*`, `mathcolor`, `mathbackground`, `class` (unless step 7 shows `mathmlfixes.css` keys on specific classes, in which case allow that exact list), and any non-MathML namespace. | Count the strips, as pele does, and log them in debug builds. |

Applying style through the CSSOM is the important CSP detail. A `style` attribute that arrives through markup parsing or `setAttribute` is blocked under a `style-src` without `'unsafe-inline'`, while `element.style.setProperty` is not. That is why alignment environments keep their layout regardless of Office's style policy. Dropping `color` loses `\color{red}`. A follow-up can map the common named colours onto daisyUI semantic tokens such as `--color-error` so they meet contrast in both themes. The `math-core` `\R` predefinition, which collides with a user's `\newcommand{\R}`, should be documented, not patched.

For the font, ship **the math-core-fonts New Computer Modern subset without `ssty` (about 200 kB)**, because that is what the converter's author tests against. **Latin Modern Math (388,212 B, GUST licence verified)** is the fallback if that subset's licence does not check out. Fira Math (95,524 B, sans-serif) is the choice if design prefers formulas to match the daisyUI UI face over a LaTeX look. Delete the CDN `<link>`/`<script>` snippet from the module docs and from the editmark-leptos guidance, and note in the CHANGELOG that `window.katex` is no longer consulted.

## What remains unverified before this ships

Seven questions are open, and the browser lane answers most of them. **Visual quality:** no session compared math-core's output with KaTeX in Chrome, Firefox and Safari, and no independent 2026 comparison exists. The only evidence comes from tool authors, who have a stake in the outcome. **Real headroom:** the 451-level trap was measured in an isolated module on a 1 MiB stack, not inside the Leptos binary, so the cap of 64 must be proven by the hostile-corpus lane. **Vocabulary drift:** math-core's tag and attribute set was measured over 20 formulas. Whether it emits `menclose`, `class`, `msqrt` or its own `annotation` for other inputs must be confirmed by running the full corpus through the sanitiser in a native test that fails on any stripped node. **Office's `style-src` and `font-src`** were not available. CSSOM styling sidesteps the first, but the font needs `font-src 'self'` (or a `default-src` that covers it). **Licences** for the math-core-fonts subset, STIX Two, Fira Math and Libertinus were not read from their LICENSE files. **The wasm increment** inside the real binary, after wasm-opt, is an estimate of 60 to 70 KB brotli. **Screen readers** other than NVDA, and the copy-paste behaviour of native MathML, have no 2026 source.

## Conclusion

The question looked like a choice of renderer, but the deciding factor is where trust boundaries and failure modes sit. A JavaScript renderer has to run in a worker because it might hang, and every consumer has to serve its assets. math-core removes the hang risk with bounded macro expansion, and its one hard failure, stack depth, is decidable from the input before the call. A lexical guard is cheaper, more testable and more portable across consumers than another worker and asset base. The design also leaves an exit: the allow-list operates on MathML, not on math-core, so if visual quality disappoints, Temml in a pele-style worker can be swapped in behind the same sanitiser, CSS and lane without touching the Markdown surface.

The move also changes what "rendered math" means for accessibility. KaTeX's HTML output gave screen readers a hidden MathML shadow. Native MathML, with a TeX annotation and no `aria-label`, is now what NVDA reads directly through MathCAT. The lane should therefore treat speakable structure as a gate, the same way it treats contrast.
